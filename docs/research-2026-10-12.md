注意: この節が対象にするのは**「投稿情報」（＝出品された商品の情報など）の収集**。本ツールが主に読むライブラリ・注文履歴は自分のアカウントの非公開データで、投稿情報そのものではない。このため、この節は本ツールを直接「許可」する根拠ではない。ただし、プログラムによる取得そのものを一律に禁じず、**負荷・権利侵害・損害**を基準に制限するという運営の姿勢を示している（公開の商品 JSON や検索の取得には直接当てはまる）。

### 1.6 結論（§7-6）

- BOOTH 個別規約（全 16 条）にも BOOTH ガイドラインにも共通規約にも、**ユーザーが自分のアカウントのデータを自分で読むことを禁じる条項は無い**。認証情報について規約が求めているのは、自分で管理すること（第10条）と、第三者へ譲渡・貸与しないこと（第11条2項）。本ツールは利用者本人のセッションを本人の端末で使うだけなので、これに当たらない（cookie を他人と共有する機能や、ホスティング型のマルチユーザー運用は作らないこと）。
- 実際に効いてくる制約は、共通規約第14条**23号（過度な負荷）・24号（機械的・短時間大量の操作）**と、ガイドラインの「サーバに極端な負荷をかける行為」。**直列・1 req/s 以下・バックオフ・本人のデータに限る**という現在の設計（PLAN §2.4）は、これらと**矛盾しない**と判断する。ただし 31 号（「その他、当社が不適切と判断する行為」）と商標ガイドラインの「停止を要求する場合がございます」で運営に裁量が残るので、止めるよう求められたら従う前提とする。
- DL したデータの扱いは規約上**各ショップの利用規約**によるので、README の現在の記述（再配布禁止などは各商品の規約に従う）で足りる。共通規約14条1号・2号から、ツールに再配布・転載を助ける機能を持たせないこと。
- 有償化・商用化するなら14条3号に当たらないかを別途確認する。
- 確信度: **高**（条文の確認）／中（運営の裁量による解釈部分）。

### 2.3 分析

1. **「BOOTH」が明示的に対象になっているわけではない。** ガイドラインが定義しているのは「pixiv(ピクシブ)という名称、ロゴ画像」だけで、BOOTH には触れていない。また「BOOTH」が商標登録されているかは**未確認**（J-PlatPat は未検索）。ただし共通規約第2条4項で「登録商標の利用ガイドライン」は全ユーザーに適用されるので、**運営は BOOTH にも同じ原則を当てはめると考えるのが安全**（類推による解釈）。
2. **基本規則は、商標と他の語を組み合わせた名前（「pixivplayer」「LookPixiv」）を禁止の例に挙げている。** `booth-library-mcp` は同じ型（商標＋一般名詞）。
3. **アプリの節で許されているのは、説明文の中で「プラットフォームを利用して開発した」と述べること**（＋非公式である旨の併記）。商標を名前に入れることまで認めているわけではなく、さらに「当社サービスと混同を招きかねない名称は避けてください」とある。
4. **最大の問題は §7-5 の結果と重なること。** 公式アプリの名前は **「BOOTH Library Manager」**（URL スキーム `booth-library-manager://`、コミュニティでの略称は BLM。例: `AmariNoa/BLM-Integration-Core`）。`booth-library-mcp` は先頭の `booth-library-` が同じで、略すと「BLM」に近く、**公式アプリと取り違えられやすい名前**。ガイドラインの「混同を招きかねない名称は避けて」に最も直接当たる。
5. 「BOOTH」を名前に含む第三者の OSS は多い（npm `booth-mcp` は登録済み〔registry 200〕、GitHub に `Kyure-A/mcp-booth`、`ribeKim/booth-library-manager` など）が、黙認されているだけで、許可された根拠にはならない。

### 3.2 deeplink はどう作られるか（ページとボタン）

1. **ページ**: `accounts.booth.pm/library`（ライブラリ）、`/library/gifts`（ギフト）、`/orders/{id}`（注文詳細）。ファイルの行ごとに「ダウンロード」ボタンと並んで **「その他のDL方法」** ドロップダウン（`div.js-download-button[data-label="その他のDL方法"][data-test="other-downloads-button"]`）がある。実ページでの件数はライブラリ 88、ギフト 5、注文詳細 3 の計 96 行。
2. このドロップダウンの `data-dropdown-items` JSON に 2 項目が入っている（固定文字列は実ページのとおり、ID はダミー）:
   ```json
   [{"text":"BOOTH Library ManagerでDL",
     "deeplinkDownloadableUrl":"https://booth.pm/downloadables/{downloadable_id}/deeplink?client=booth-library-manager&variation_id={variation_id}",
     "fallbackUrl":"https://booth.pm/announcements/893",
     "fallbackMessage":"アプリの起動に失敗しました。ご案内ページに移動しますか？"},
    {"text":"VRoid StudioでDL",
     "deeplinkDownloadableUrl":"https://booth.pm/downloadables/{downloadable_id}/deeplink?client=vroid&variation_id={variation_id}",
     "fallbackUrl":"https://vroid.pixiv.help/hc/ja/articles/52782908405273", "fallbackMessage":"（同上）"}]
   ```
   `client=vroid`（VRoid Studio も pixiv の製品）の項目もあることから、これは **BOOTH が自社アプリへ受け渡すための仕組み**で、`client` はどちらの自社アプリかを指定するパラメータだとわかる。
3. **クリック時の処理**（`https://asset.booth.pm/assets/a740dbd80d917435e327.js`。`.js-download-button` 用に遅延読み込みされる webpack チャンク 49557。抜粋）:
   ```js
   const o=((e,t)=>{const r=window.setTimeout(()=>{confirm(t)?window.location.href=e:n()},1500); … })(r,n),
   a=()=>{o.cancel(),window.removeEventListener("blur",a,!0),window.removeEventListener("pagehide",a,!0)};
   window.addEventListener("blur",a,!0),window.addEventListener("pagehide",a,!0),window.location.href=t
   ```
   → ブラウザを https の `deeplinkDownloadableUrl` へ移動させ、1.5 秒以内にウィンドウが blur / pagehide しなければ（＝アプリが起動しなければ）`confirm(fallbackMessage)` を出し、OK なら案内ページ 893 へ移動する。
4. **サーバー側（未検証・推定）**: `/downloadables/{id}/deeplink` がカスタムスキーム `booth-library-manager://item-import?dlurl=…&downloadable_filename=…&item_id=…&order_id=…&variation_id=…` へリダイレクトし、OS がそれをアプリに渡すと考えられる。根拠は、JS が https の URL へ移動しているだけであることと、`tukiminya/omnooth` がこの形式の URI を受け取って処理していること（README「これで、BOOTHから開かれた `booth-library-manager://` URLをomnoothが受け取れるようになります。」「ギフト商品では `order_id` が省略されることがありますが、そのまま取り込めます。」、`internal/importer/uri.go` の必須パラメータは `dlurl` `downloadable_filename` `item_id` `variation_id`）。`dlurl` は booth.pm 配下の HTTPS URL（omnooth `url.go` の許可リスト）で、omnooth は「dlurlには署名情報が含まれる可能性がある」とコメントしている。**ステータスコード（302 かどうか）と Location は実測していない**。確認するなら、ログインした状態でリダイレクトを追わずに 1 回だけリクエストし、Location のスキームとパラメータ名だけを記録する（署名付き URL はログに残さない）。
5. Windows ではスキームを `HKCU\Software\Classes\booth-library-manager` に登録する（omnooth の `registrar_windows.go`。説明文字列は "URL:BOOTH Library Manager Protocol"）。公式アプリも同じキーを使っていると推定されるが、**未確認**。

### 3.3 第三者のツールが「公式の DL 受け渡し口」として使えるか → **使えない（公式に用意されたものではない）**

- 告知・ヘルプ・規約のどこにも、第三者向けの API や受け渡し仕様の公開、利用許諾は無い。`client=booth-library-manager` / `client=vroid` は自社アプリを指す識別子で、**第三者が名乗ることは想定されていない**。
- 考えられる使い方とその評価:
  - (a) **`booth-library-manager://` を自前で登録する**（omnooth の方式）: 公式アプリのスキームを横取りすることになり（HKCU のキーを上書きするので、公式アプリをあとから入れた／入れていた利用者の環境を壊す）、利用者が公式アプリと取り違えるおそれもある。共通規約14条15号（なりすまし、または誤認されるおそれ）や、商標ガイドラインの「当社から発行/配信されていると誤解されるような表現は禁止」に**抵触するリスクがある**。Stashly は意図的にこれを避けている（docs/decisions/0001-isolated-booth-webview.md: "The global `booth-library-manager://` protocol registration is not read or changed."）。**採らない。**
  - (b) **本ツールが `/deeplink?client=booth-library-manager` を自分で叩いて Location から `dlurl` を取り出す**: 公式アプリになりすますことになる。しかも得られる `dlurl` は、すでに使っている `/downloadables/{id}` の 302 先（§7-4 で `s6.booth.pm` と実測）と同じ種類の署名付き URL と考えられ、**得るものが無い**。`variation_id` も「その他のDL方法」の JSON から読める（§7-13）。**採らない。**
  - (c) **（任意・低リスク）ページにある `deeplinkDownloadableUrl` をそのまま利用者に見せ、利用者が自分のブラウザで開く**: 利用者が BOOTH 上でボタンを押すのと同じで、本ツールは何もリクエストしない。公式アプリを入れている人への「公式 BOOTH Library Manager で開く」導線にはなるが、非公開の仕様なので予告なく変わりうるし、アプリもアーリーアクセス・Windows のみ・Discord 配布。入れるとしても補助的な表示にとどめる。
- 結論: DL 機能は現状どおり、**明示的に有効にしたときだけ `/downloadables/{id}` を使う**。BOOTH Library Manager の受け渡し口に乗っても安全にはならない（§7-5 の「公式の受け渡し口なら乗る方が安全かも」という仮説は**否定**）。
- 確信度: 公式アプリであることは**高**。deeplink の仕組みは**中**（ブラウザ側は実コードで確認、サーバーのリダイレクトは推定）。
